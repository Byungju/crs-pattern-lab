# 901001 — CRS 설정 누락 감지 (crs-setup.conf)

- **파일**: `REQUEST-901-INITIALIZATION.conf` (line 54)
- **phase**: 1
- **action**: `deny`, `status:500`, `log`, `auditlog`
- **로그**: error log + audit log
- **검증**: [`tests/901001.sh`](tests/901001.sh)

## 룰 원문

```
SecRule &TX:crs_setup_version "@eq 0" \
    "id:901001,\
    phase:1,\
    deny,\
    status:500,\
    log,\
    auditlog,\
    msg:'CRS is deployed without configuration! Please copy the crs-setup.conf.example template to crs-setup.conf, and include the crs-setup.conf file in your webserver configuration before including the CRS rules. ...',\
    tag:'OWASP_CRS',\
    ver:'OWASP_CRS/4.30.0-dev',\
    severity:'CRITICAL'"
```

**한 줄 요약**: `crs-setup.conf` 가 CRS rules **앞에 로드되었는지** 확인하는 안전장치.
로드되지 않았으면 HTTP **500** 으로 요청을 중단시킨다.

## 핵심: `&TX:crs_setup_version` 은 "값"이 아니라 "개수"

이 룰에서 가장 헷갈리는 지점은 **`&` 접두사**다.

| 표기 | 의미 |
|------|------|
| `TX:crs_setup_version` | 변수의 **값** (예: `4300`) |
| `&TX:crs_setup_version` | TX 컬렉션에 그 이름의 변수가 **몇 개 있는지** (없으면 `0`, 있으면 `1`) |

즉 이 룰은 "값이 0인가?"가 아니라 **"`crs_setup_version` 이라는 변수가 아예 없는가?"** 를 검사한다.

| 상황 | `TX:crs_setup_version` 값 | `&TX:crs_setup_version` 개수 | `@eq 0` | 룰 |
|------|---------------------------|------------------------------|---------|-----|
| 정상 (`crs-setup.conf` 로드됨) | `4300` | `1` | false | 매칭 안 됨 |
| 오설정 (`crs-setup.conf` 누락) | (변수 없음) | `0` | true | **매칭 → 500** |

> ⚠️ **혼동 주의**: 검증 로그에 아래처럼 `TX:crs_setup_version (Value: 0)` 로 찍힌다.
> ```
> Matched "Operator `Eq' with parameter `0' against variable `TX:crs_setup_version' (Value: `0' )
> ```
> 여기서 `Value: 0` 은 **변수 값이 0** 이라는 뜻이 아니라, `&` 가 반환한 **개수 0(변수 없음)** 이다.
> (값을 비교하는 룰이었다면 `Value: 4300` 처럼 찍혔을 것이다.)

## 왜 값(4300)이 아니라 개수(0)로 비교하나

- `crs_setup_version` 의 값은 CRS 버전에 따라 달라진다(현재 `4300` = v4.30.0).
  값으로 비교하면 버전이 바뀔 때마다 깨진다.
- 알고 싶은 것은 "**설정 파일이 로드되었는가**" 이므로 **존재 여부(개수)** 가 정확한 조건이다.
- 같은 idiom 이 이 파일 곳곳에 쓰인다: `SecRule &TX:blocking_paranoia_level "@eq 0"` 등은
  "사용자가 값을 지정하지 않았을 때만 기본값을 넣는다" 는 의미다.

## 동작

매칭 시:
- `deny,status:500` → 요청을 **500** 으로 차단. (클라이언트 잘못이 아니라 **서버 설정 오류**이므로 4xx가 아닌 5xx)
- `log,auditlog` → error log + (설정돼 있으면) audit log 에 위 msg 기록.

## 정상 / 비정상 흐름

```
정상:
  modsecurity.conf            (엔진 설정)
  → crs-setup.conf            (900990: setvar tx.crs_setup_version=4300)  → 개수 1
  → rules/REQUEST-901-...     (901001: &TX:crs_setup_version == 0 ? no)   → 통과

오설정:
  modsecurity.conf
  → rules/REQUEST-901-...     (crs-setup 미로드 → 변수 없음 → 개수 0)      → 901001 매칭 → 500
```

핵심은 **rules 파일(`901001` 이 든 파일)은 crs-setup 과 별개로 로드된다**는 점이다.
그래서 "crs-setup 만 빠진" 상황에서도 901001 룰 자체는 정상 로드되어 검출할 수 있다.

## 검증 (재현)

`tests/` 는 **crs-setup 을 include 하지 않은** 별도 설정을 만들어 이 상태를 재현한다.

## 참고

- `crs_setup_version=4300` : CRS v4.30.0 을 나타내는 숫자(예: v3.0.0 → 300).
- `auditlog` 는 `SecAuditEngine` 이 유효할 때만 audit 로그에 남는다. 테스트 설정에는
  `SecAuditEngine` 이 없어 **error log** 로 확인한다.
- `severity:'CRITICAL'` 이지만 어노말리 점수에는 반영되지 않는다(즉시 deny).
