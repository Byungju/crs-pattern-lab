# 905100 — Apache SSL pinger 예외 (조건 불일치로 미발동)

- **파일**: `REQUEST-905-COMMON-EXCEPTIONS.conf` (line 17)
- **phase**: 1
- **action**: `pass`, `nolog` → chain → `ctl:ruleRemoveByTag=OWASP_CRS`, `ctl:auditEngine=Off`
- **로그**: 없음(nolog)
- **검증**: [`tests/905100.sh`](tests/905100.sh) — **SKIP(미발동)**

## 룰 원문

```
SecRule REQUEST_LINE "@streq GET /" \
    "id:905100, phase:1, pass, t:none, nolog, ... chain"
    SecRule REMOTE_ADDR "@ipMatch 127.0.0.1,::1" \
        "t:none, ctl:ruleRemoveByTag=OWASP_CRS, ctl:auditEngine=Off"
```

## 의도

Apache 의 **SSL pinger**(로컬 헬스체크)가 보내는 `GET /` 요청을 오탐 없이 통과시키기 위해,
로컬 주소(`127.0.0.1`, `::1`)에서 온 `GET /` 에 대해 CRS 룰 전체를 제거하고 audit 을 끈다.

## 조건

| 항목 | 값 |
|------|-----|
| `REQUEST_LINE` | `@streq GET /` (정확히 `GET /`) |
| `REMOTE_ADDR` | `@ipMatch 127.0.0.1,::1` |

## 실측: 이 환경에서는 발동하지 않음

`REQUEST_LINE` 을 probe 로 확인한 결과 **`GET / HTTP/1.1`** (프로토콜 포함)이다.
따라서 `@streq GET /` 와 **불일치**하여 905100 은 매칭되지 않는다.

- 검증: `GET /` + `Host: 127.0.0.1`(=원래 920350 이 뜨는 조건) 요청 시
  920350 이 **그대로 기록**됨 → CRS 가 제거되지 않았음(=예외 미적용).
- 같은 이유로 `ctl:auditEngine=Off` 도 적용되지 않는다.

```
./tests/905100.sh
실제 REQUEST_LINE: GET / HTTP/1.1
SKIP 905100: 조건(@streq GET /) 불일치로 실환경 미발동 — 발동 검증 불가
```

> 참고: 같은 파일의 905110 은 `REQUEST_LINE` 을 `^(?:GET /|OPTIONS \*) HTTP/[12]\.[01]$`
> 처럼 **프로토콜을 포함**해 매칭하므로 정상 동작한다. 905100 의 `@streq GET /` 는
> 프로토콜을 포함하지 않아 v3/nginx 에서 매칭될 수 없다(의도와 실제 동작 불일치로 보임).

## 배경: 왜 이런 룰이 기본 포함되어 있나

- **기원**: 2014년 Ryan Barnett 이 `base_rules/REQUEST-01-COMMON-EXCEPTIONS.conf` 에 추가한
  **Apache 전용 예외** 룰이다. (CHANGES: `exception for Apache SSL pinger (Request: GET /)`)
  이후 룰 id 만 `901100 → 905100` 으로 재번호되었다.
- **대상**: Apache `mod_ssl` 의 **SSL pinger**(로컬 헬스체크)가 보내는 요청을 오탐 없이 통과시키는 것.
  이때 요청 라인을 `GET /`(HTTP 버전 생략)로 가정해 `@streq GET /` 로 작성되었다.
- **CRS 는 다중 엔진/플랫폼 공용 단일 룰셋**: Apache(ModSecurity v2), nginx(v3), IIS, Coraza 등이
  같은 `rules/*.conf` 를 공유한다. `REQUEST_LINE` 등 **변수의 값/의미가 커넥터마다 다를 수 있는데**,
  CRS 는 한 벌의 룰을 유지하기 위해 이런 차이를 안고 간다.
  - nginx + libmodsecurity v3 에서는 `REQUEST_LINE` 이 항상 `GET / HTTP/1.1` 형태이므로
    `@streq GET /` 는 **사실상 no-op** 이 된다.
- **그럼에도 기본 제공되는 이유**
  1. 다른 플랫폼/엔진(특히 Apache)에서는 의도대로 동작할 수 있는 **공용 룰**이다.
  2. **안전하다**: 조건에 `REMOTE_ADDR @ipMatch 127.0.0.1,::1` 가 있어 **로컬 요청에만** 적용되므로,
     발동 여부와 무관하게 원격 사용자에 대한 보안 영향이 사실상 없다.
  3. **룰 ID 안정성(하위 호환)**: 사용자가 `SecRuleRemoveById 905100` 등으로 참조할 수 있어,
     동작하지 않더라도 ID 를 함부로 삭제하지 않는 관례가 있다.
  4. "오탐 완화" 목적의 예외 룰이라 없어도 치명적이지 않아 굳이 제거하지 않는다.

## nginx 에서 의도한 효과를 얻으려면

905100 대신, 실제 값(`GET / HTTP/...`)에 맞춰 직접 예외를 정의한다. 예:

```
# 로컬에서 오는 "GET / HTTP/x.y" 를 예외 처리
SecRule REQUEST_LINE "@beginsWith GET / HTTP/" \
    "id:1000100,phase:1,pass,nolog,chain"
    SecRule REMOTE_ADDR "@ipMatch 127.0.0.1,::1" \
        "t:none,ctl:ruleRemoveByTag=OWASP_CRS,ctl:auditEngine=Off"
```

## 참고

- 예외 적용 시 효과: `ruleRemoveByTag=OWASP_CRS`(해당 트랜잭션에서 CRS 전 룰 제거) + `auditEngine=Off`.
- `nolog` 라 로그가 남지 않으며, 효과 자체를 다른 룰(920350)의 유무로 간접 검증한다.
